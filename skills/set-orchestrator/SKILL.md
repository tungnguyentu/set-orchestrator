# Set orchestrator

Gives this session a durable coordinator role: **bind a Run -> list same-pane agents -> write state file -> delegate everything, code nothing**. Write Task specs and reports in the user's language; this file is English only.

Version-matched Orca docs come from the binary: `ORCA skills get orchestration` (and `--reference references/<name>.md`). Do not copy them here. The detailed loop, error table and short brief template are in `references/coordinator-loop.md`; the worker rules every brief relies on are in `references/worker-contract.md` (installed per pane as `.orca/worker-contract.md`).

## 0. Orca CLI

Resolve the executable in this order: `$ORCA_CLI_COMMAND` when set (Orca exports it inside its terminals); `orca-dev` when `$ORCA_DEV_REPO_ROOT` is set (a dev checkout); `orca-ide` on Linux outside an Orca-managed terminal; otherwise `orca`. Below, `ORCA` is a placeholder for it; never hardcode `orca`. Always pass `--json`. Scripts live in this skill's `scripts/` directory; call them by path relative to the skill directory.

State file: `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/orchestrator/<self-handle>.json`, holding `{run_id, self_handle, pane_path, roster[], opened[], autocompact[], skill_family, started, objective, gate, dispatches[]}` (`opened[]` = handles of terminals this role created); each `dispatches[]` entry is `{task_id, dispatch_id, terminal, agent, title, base_title, wave, status, attempt, started, settled, spec_hash, checklist, report, spec_path, pane, gate_hash, verify}` and is updated at every dispatch, settlement and retry (`scripts/dispatch.sh` and `scripts/settle.sh` write it under a lock). `spec_hash` is the trusted specHash of the Task's checklist; `<state dir>/specs/<task>.json` is the coordinator-side copy of the hashed spec and `<state dir>/briefs/<task>.txt` the brief sent. Both live outside the worktree, so workers cannot rewrite them. It is how the role survives compaction or a new session.

## Role rules while active

- Do not edit product code. Allowed directly: read code to write specs, verify diffs, run read-only checks/tests, answer the user.
- Send work only to terminals whose `worktreePath` equals the pane path. Orca does NOT enforce this (a cross-pane dry-run succeeded), so you must. Never target another pane, even if the user's agent type is only open there; say so and ask the user to open one in this pane.
- Never send to a busy terminal or to a user's live work without permission. Never open a new terminal (`scripts/open-agents.sh` or `worker-start --agent`) unless the user asks, with `--open` or in words. Never `ORCA orchestration reset`.

## Anti-skip contract (all agents)

Applies to every worker type (claude, grok, codex, agy). The critical path is shell scripts + brief rules + your own verify; no agent hook is required (Claude Stop hooks are an optional extra). Full detail, schema and agent notes: `references/multi-agent-anti-skip.md`. `SKILL` = absolute path of this skill directory (workers need absolute paths).

- **Completion only through the gate.** Every brief tells the worker to finish ONLY with `bash SKILL/scripts/orca-done.sh --from $W --task $TASK --dispatch $DISPATCH --checklist <path> --report <path> --expect-spec-hash <specHash> --summary "..."` (`--outcome failed` when an item is not done). It runs `verify-checklist.py` (items + evidence, report, protected-path diff, acceptance reruns) and sends `worker_done` only on pass, with the DONE-WHEN lines built from the checklist file. Raw `orchestration send --type worker_done` is allowed only when the script is unavailable in that terminal and you answered the worker's `ask` saying so.
- **Short brief + worker contract.** <!-- worker-contract:skill-md --> Reply/ask/heartbeat/escalation commands, the start ritual, mark-item/write-report usage, completion rules and the Method/Context lines live once in `<pane>/.orca/worker-contract.md` (`scripts/install-worker-contract.sh`, step 8b of `on`). The per-dispatch brief is the SHORT form in `references/coordinator-loop.md` (header with ids and paths, the `Finish ONLY: … orca-done.sh …` line, Goal/Change/Ownership/Out of scope/Acceptance, `Done-when: see checklist`); its first line tells the worker to read the contract once if new. Never paste the contract text, the Method/Context lines or the ask rule into a brief.
- **Checklist before dispatch, trusted specHash.** <!-- anti-skip:spec-hash --> `scripts/dispatch.sh` runs `init-checklist.py` (items = the spec's Done-when list), which writes `<pane>/.orca/tasks/<taskId>/checklist.json` and prints its `specHash` (sha256 over taskId, baseRef, items[id, step], protectedPaths, acceptanceCommands). `.orca/` is worker-writable, so the checklist's own `specHash` field proves nothing: the coordinator stores the printed value as `dispatches[].spec_hash` (plus `specs/<task>.json`) and ALWAYS verifies with `--expect-spec-hash` (what `settle.sh` does). A hash mismatch or missing `spec_hash` fails before any acceptance command runs.
- **Parallel only on disjoint paths.** <!-- anti-skip:parallel-wave --> Put Tasks in one wave only when their Ownership and Protected paths do not overlap (no file or prefix in one Task's Ownership is in another's Ownership or Protected). Otherwise serialize them with `--deps`. `--protected-diff` looks at the whole worktree, so a concurrent Task that edits another Task's protected path makes that Task's gate fail falsely; judge such a hit from `git log` before retrying.
- **One concern per Task.** Prefer one Task per concern chained with `--deps`. For multi-step or risky work add a `verify-<title>` Task that depends on the implement Task, goes to a different idle terminal when one exists, reruns the gate and acceptance itself, and does not trust the implement worker's prose or report.
- **Spec fields** (in addition to loop step 1): Original goal (user's words), In scope, Out of scope, Done-when (numbered, same as checklist), Protected paths (tests, fixtures, snapshots, CI config, plus the Ownership of already settled Tasks; never the Ownership of a Task in the same wave, which the wave rule above keeps disjoint and step 5 checks from the diff; never weaken or skip tests). Start ritual, heartbeat, evidence, ask and completion rules are in the worker contract and `orca-done.sh`; never restate them in the spec or brief.
- **Frozen gate.** <!-- anti-skip:gate-snapshot --> Workers run as your OS user in bypass mode and can edit this skill's scripts. `dispatch.sh` therefore freezes the gate scripts read-only into `<state dir>/gate/<hash>/` (first dispatch of a state file; later dispatches stop with exit 4 if the skill's scripts changed, `--accept-gate-change` only when you changed them) and prints that copy's `settle.sh` as `settle`. Always run that frozen `settle.sh`; it fails the Task when the copy no longer matches its hash or when the skill dir's gate scripts differ from it (the worker's `orca-done.sh` ran from the skill dir).
- **Verify** (loop step 5) always runs the frozen `settle.sh` yourself, whatever the body says; a raw `worker_done` without the `DONE-WHEN:` / `gate:` lines, `gate: SKIPPED`, a specHash mismatch, a protected-path diff, a failed rerun, or evidence that does not hold (unknown commit, missing file:line) is a verification failure (first failed attempt). Plain-text evidence is only a warning (`unverifiedItems`): check those items yourself.

## `on [objective] [--from <handle>] [--open <agent>[:<count>],...] [--skills ak|ce|superpowers|none]`

1. `ORCA status --json` to confirm the app is up.
2. Self handle: `bash scripts/self-handle.sh [--from <handle>]`. It prints `$ORCA_TERMINAL_HANDLE` or the `--from` value; exit 2 means this session is outside an Orca terminal, so run `ORCA terminal list --json`, find the terminal in the current pane that is this session (ask the user if more than one candidate), and tell the user which handle you chose before creating a Run. Only `$ORCA_TERMINAL_HANDLE` proves identity.
3. Pane path = `worktreePath` of the self terminal (from `terminal list`).
4. `ORCA orchestration run-current [--from $SELF]`. If a Run is bound, reuse it; otherwise `ORCA orchestration run-create --objective "<objective or 'orchestrate <pane>'>" [--from $SELF]`.
5. Open agents (only with `--open`, or when the user asks in words, for example "mở thêm 2 claude và 1 grok"): `bash scripts/open-agents.sh --pane "<pane path>" --open <spec> --next <n>` with `<spec>` such as `claude:2,grok,codex,agy` and `<n>` the next free roster number. It runs `ORCA terminal create --worktree path:<pane> --title <agent>-<n> --command <launch>` per agent, where `<launch>` sets the permission mode: Claude `cc-launch --permission-mode auto` (bypass is disabled in the global settings; inherits your `CLAUDE_CONFIG_DIR`, so the worker uses your account and the shared Serena), Grok `--permission-mode bypassPermissions`, Codex `--dangerously-bypass-approvals-and-sandbox`, Antigravity (`agy`) `--dangerously-skip-permissions`. It then waits for `tui-idle` and `agentIdentity`, printing one JSON row per terminal (`handle, agent, title, ok, error`). A row with `ok:false` is reported to the user as is; never retry the launch blindly. Terminals it opened are yours: `ORCA terminal close --terminal <h>` on `off` when the user agrees.
6. Roster: `ORCA terminal list --json | python3 scripts/pane-roster.py --pane "<pane path>" --self $SELF` (`--json` for machine use). Eligible rows = same pane + agentIdentity set + connected + writable + not busy + not self. If none are eligible, say so plainly and stop: ask the user to open an agent in this pane or to rerun with `--open`.
7. Skill family. `--skills` wins; otherwise detect from this session's config dir `${CLAUDE_CONFIG_DIR:-$HOME/.claude}`: `skills/ak-cook` present means `ak`; else a `plugins/cache/*/compound-engineering` directory means `ce`; else `plugins/cache/*/superpowers` means `superpowers`; else `none`. Store it as `skill_family`; it picks the Method and Context lines that step 8b writes into the pane's worker contract (table in `references/coordinator-loop.md`). Workers started from another config dir or another machine may differ: when a `worker_done` body says the skill is not installed, tell the user and suggest `--skills`.
8. Write the state file (`mkdir -p` its directory).
   8b. Worker contract (once per pane, not per worker): `bash scripts/install-worker-contract.sh --pane "<pane path>" --skill "<abs skill dir>" --family <skill_family> [--orca <resolved ORCA>]`. It writes `<pane>/.orca/worker-contract.md` from `references/worker-contract.md` with this skill's absolute path and the family's Method/Context lines, and adds `.orca/` to `.git/info/exclude`. Rerunning is safe: an existing file only gets its skill/Method/Context blocks refreshed (`--force` rewrites it whole). If `--skills` changes later, rerun with the new family.
9. Auto-compact window. For every eligible Claude terminal (`agent` starts with `claude`): `ORCA terminal wait --terminal <h> --for tui-idle --timeout-ms 60000`, then `ORCA terminal send --terminal <h> --text "/autocompact 300k" --enter --wait-submit 15 --json`; record the handle in the state file's `autocompact[]` list. Queue the same input to yourself: `ORCA terminal send --terminal $SELF --text "/autocompact 300k" --enter` (it runs when this turn ends). The command persists `modelSettings.<model>.autoCompactWindow: 300000` in that session's `settings.json`, so it is cheap to repeat. Skip Codex, Grok and Gemini terminals (no such command).
10. Names. `ORCA terminal rename --terminal $SELF --title "orchestrator"`, then every eligible worker: `ORCA terminal rename --terminal <h> --title "<agent>-<n>"` (agent type plus its position in roster order; terminals from step 5 already carry such a title, keep it). Store each title in the state file `roster[]` entry. Orca prepends its own status glyph; never include one in the title.
11. Tell the user: "This session is now orchestrator for pane X, Run R, N agents: ..." and say that from now on implementation requests go through the dispatch loop.

Outside an Orca terminal, `run-create`, `run-current`, `send`, `reply`, `task-create`, `task-update`, `dispatch`, `worker-start` need `--from $SELF`; `check` needs `--terminal $SELF` and rejects `--from`; `worker-list/show/read/release/retain/abandon` need neither.

## Coordinator loop (summary; details in `references/coordinator-loop.md`)

1. **Spec.** Per Task, write a self-contained spec: Target, Change, Constraints, Ownership (files it may edit), Observable acceptance (exact test and build commands), Skill (the worker contract's Method line for the state file's `skill_family`, not repeated per brief: `/ak:cook` or `/ak:debug` then `/ak:fix`; `/ce-plan` and `/ce-work` or `/ce-debug`; superpowers `writing-plans`, `executing-plans` or `systematic-debugging`; add a domain skill when one fits, for example `/ak:frontend-development` or `/ce-test-browser`, so the worker loads it first; on the compact path name it in the brief's `Change:` line); plus "commit (unless the user asked for no commit), do NOT push, do NOT deploy; do not `git add -A`; state the branch". Every Task that touches UI, API, data access or static assets also carries the performance checklist in its Constraints (list in `references/coordinator-loop.md`, section "Performance checklist"): the worker must not add a regression on any item and must report what it checked. Done-when checklist (required): every Task spec includes a numbered Done-when list (3–8 items). Each item must be observable (file path, command, or UI check the coordinator can re-run). Never replace this with "implement X end-to-end" or a vague Method-only brief. If the user's request has more than ~8 observable steps, split into multiple Tasks with `--deps` instead of one mega-spec. The worker may not invent extra steps that skip a listed item. Evidence, the ask rule and completion are covered by the worker contract (`.orca/worker-contract.md`) and `orca-done.sh`, which builds the DONE-WHEN lines from the checklist; do not repeat them in the spec. A vague spec makes the worker `ask` instead of work.
2. **Pick terminals.** Re-run the roster. When the user asks for more agents mid-run ("mở thêm 1 codex"), run step 5 of `on` with `--next` set past the highest roster number, add the handles to `opened[]`, and continue with them as new terminals. Make sure `<pane>/.orca/worker-contract.md` exists (rerun step 8b; a no-op when current; once per pane, never per worker); a new worker reads it via the brief's first line. A Claude terminal that is not yet in the state file's `autocompact[]` list (opened after `on`) gets `/autocompact 300k` as in step 9 of `on` before its first brief. When the user names a worker by its tab title (for example "giao cho 2FA"), resolve it with `python3 scripts/pane-roster.py --pane "<pane path>" --self $SELF --title "<text>"`: case-insensitive substring match on the `title` column, status glyph ignored, same pane only. Exit 3 (no match) or 4 (several matches, listed on stderr): show the user the candidates and ask which one; never guess and never widen the search to other panes. Titles are yours to manage (step 10 of `on`): a terminal that joined after `on` gets `<agent>-<n>` with the next free number before its first brief. Before each start, `ORCA terminal show --terminal <h> --json` must show `agentIdentity`, and `ORCA terminal wait --terminal <h> --for tui-idle` must be satisfied (an agent mid-command yields `agent_unconfigured`). One active Dispatch per terminal.
3. **Start the wave (compact brief, default).** One line per Task: `bash scripts/dispatch.sh --from $SELF --to <h> --title "<title>" --spec-file <spec.md> --goal "<user's words>" --change "<1-2 sentences>" --ownership "<paths>" --out-of-scope "<short>" --acceptance "<cmd>"... --protected <glob>... [--deps '<json>'] [--wave N] [--attempt N]` (`--task <id>` to reuse a Task; `--dry-run` to preview). It refuses a spec with no Done-when list or more than 8 items, then: `task-create`, `init-checklist.py` (stores `specHash`), `install-worker-contract.sh` (no-op when current), `dispatch` **without `--inject`**, the short brief (template in `references/coordinator-loop.md`; its `Finish ONLY:` line carries `--expect-spec-hash`), `terminal send`, tab rename to `<agent>-<n> · <short title>` (40 chars max), and the `dispatches[]` entry with `spec_hash`. Re-running it for the same `--task` reuses the checklist and dispatch. It prints one JSON line (`taskId, dispatchId, specHash, checklist, report, brief`); exit 1 means an Orca step failed (the entry's `status` says which). Glance once with `ORCA terminal read --terminal <h> --limit 40`: an accepted send does not prove the agent began. Context-only Dispatches show as `unsupervised`/`retained` with no liveness: rely on heartbeats, `check --wait` and `terminal read`. Use `worker-start --task <id> --terminal <h> --worktree path:"<pane path>"` instead only when the user wants Orca's full preamble and supervision (then run `init-checklist.py` yourself and record `spec_hash`), and `worker-start --agent <id>` only when the user asks for a new terminal; read exit code and `result.state/failedStage/lastError`, not just `ok`.
4. **Wait.** `ORCA orchestration check --wait --types "worker_done,escalation,question" --timeout-ms 540000 --terminal $SELF`, run as a background shell command (a foreground command dies at 600 s). When it returns, process the whole Delivery before `--ack`: forward every `question` and `escalation` to the user one at a time, then `ORCA orchestration reply --id <msg_id> --body ... [--from $SELF]`; match `worker_done.payload.dispatchId` to the Dispatch you await and check `outcome`; then `check --ack <delivery_id> --wait ...` again in the background. An empty return is a checkpoint: loop until every dispatch in the state file is settled. Never end your turn while one is still active.
5. **Verify** yourself, because an agent can overstate what it did: `bash <state dir>/gate/<entry gate_hash>/settle.sh --from $SELF --task <id> --rename-back` (the `settle` path `dispatch.sh` printed; `scripts/settle.sh` re-executes that copy, but a worker could have edited it) (gate with the stored specHash, status `settled` or `verify_failed` in the state file, tab title restored), then `git log --oneline -3`, `git show --stat <hash>`, read the diff; check that it stays inside the spec's Ownership and that out-of-scope files were not damaged; check that reported test counts are plausible, and rerun the acceptance commands when in doubt. For a no-commit Task use `git status --short`, read the changed files and `worker_done.payload.filesModified`.
6. **Account for completion** (reuse, retain, or release) per the reference; reused terminals are never closed by release.
   - **Reused worker context.** Before sending a new brief to a terminal that already worked, `ORCA terminal read --terminal <h> --limit 20` and look for Claude Code's status line (`Context ██░░ NN%`). Above 70 %, send `/clear` (`terminal send --text "/clear" --enter`, wait for tui-idle) first; the next brief's first line makes the worker re-read `.orca/worker-contract.md`. Only on an idle terminal whose previous Dispatch is settled. Other agents: use their equivalent if known, otherwise skip.
   - **Own context.** At every wave boundary and after each `check --wait` return, `ORCA terminal read --terminal $SELF --limit 20` and read your own `Context ██░░ NN%` line. Above 70 %: update the state file, write `plans/handoffs/session-handoff.md` (relative to the pane path) in this turn: with `/ak:handoff "orchestrator <run_id>" --output plans/handoffs/session-handoff.md --force` when `skill_family` is `ak`, with `/ce-handoff create "orchestrator <run_id>"` copied to that path when it is `ce`, otherwise by hand (the continuation contract: Run, state file, active dispatches, open questions, next action), then queue two inputs to yourself with `ORCA terminal send --terminal $SELF --enter --text ...`: first `/compact keep: orchestrator role, run id, state file path, plans/handoffs/session-handoff.md, active dispatches and their terminals, forwarded questions`, then `/set-orchestrator status, then continue the coordinator loop`; end the turn so the queue runs. Step 9 of `on` sets a 300k auto-compact window as a safety net, but auto-compact runs no handoff, so this manual pass must come first. Never do this while a `question` is unanswered; reply first.
   - **Performance checklist.** In step 5, read the diff against the five items in `references/coordinator-loop.md` (unnecessary re-renders, bundle size and lazy loading, requests and caching, slow queries and N+1, images, fonts and scripts). A regression, or a worker_done body that does not say what it checked, is a verification issue: note it in the report with file:line and name the item in the retry spec. Items that the diff cannot affect (a backend-only change and re-renders, for example) are marked not applicable, not skipped silently.
   - **Done-when and gate.** <!-- anti-skip:multi-agent:verify --> `settle.sh` exit 2 fails the Task; read its JSON `errors` (missed item, evidence that does not hold, specHash, protected path, acceptance) and retry with "Previous attempt missed Done-when: <items>" plus the same Ownership/acceptance. Exit 0 still needs your eye on `unverifiedItems` (plain-text evidence) and on whether evidence matches the diff. Do not accept `succeeded` on an incomplete checklist even if tests pass. For multi-step Tasks prefer the `verify-<title>` Task over checking alone (`references/multi-agent-anti-skip.md`).
   - **Skill use.** In step 5, also check that the worker followed the Method line: a `worker_done` body or transcript (`worker-read --dispatch <id> --source transcript`) with no skill invocation for an implementation or bug Task is a verification issue; note it in the report and name the skill in the retry spec.
   - **Failed Task.** Retry exactly once: `task-create` a new Task whose spec adds "Previous attempt failed: <reason from worker_done body>" and the same deps, dispatch it the same way (`dispatch.sh ... --attempt 2`), so the state file records `attempt: 2`. A verification failure for an incomplete Done-when checklist counts as the first failure even when worker_done said `succeeded`; create the retry Task the same way. A second failure stops that Task; continue Tasks that do not depend on it and list it in the final report.
7. After 3 empty waits, `ORCA orchestration worker-list --run <run_id> --json` and follow each row's `projection.nextAction`.
8. **Final report** (one message when every dispatch is settled, or when the run is stuck): first line done/not done; a table with one row per Task: title, agent and terminal, outcome, commit hash or `no commit`, tests reported, your own verification (ok / issue with file:line), the performance checklist result per Task (ok, regression with file:line, or n/a per item); the questions forwarded to the user and the answers given; retried Tasks and why; anything left open and the next step. Nothing between dispatch and this report except forwarded questions.

## `status`

Read the state file for this self handle (a fresh session outside Orca does not know it: `ls "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/orchestrator/"`; one file means that handle, several means ask the user). If `<pane path>/plans/handoffs/session-handoff.md` exists and is newer than the state file's `started`, read it first: it is the continuation contract written before the last compaction. Then `run-current [--from $SELF]`, `ORCA orchestration worker-list --run <run_id> --json`, and the current roster. Print Run, pane, active/settled dispatches, and who owes a decision. Use it to restore the role after compaction or in a fresh session (if the state file is missing, say the role is not active).

## `off`

1. `ORCA orchestration worker-list --run <run_id> --terminal-state reclaimable --json`; for each row still owing a decision, ask the user or `worker-retain`; run `worker-release` only when told to or when it is the owned worker you created. Terminals the user opened come back `retained/external_terminal` and are never closed.
2. Active Dispatches: tell the user; do not abandon or stop without their word.
3. Terminals in `opened[]` that are idle: ask the user once whether to close them, then `ORCA terminal close --terminal <h> --json` for each agreed handle. No `reset`. Delete the state file. Tell the user the role is removed.

## Fallback (two separate branches)

**Branch A, agent type known not to honor the Orca preamble.** Skip Task and Dispatch (so there is nothing to abandon) and use the feedback-block path: generate a nonce (`openssl rand -hex 3`), send the same spec with `ORCA terminal send --terminal <h> --text "$(cat <brief>)" --enter --wait-submit 15 --json`, and end the brief with: "MANDATORY when done: print a block that opens with the line `FB-START` and closes with the line formed by joining `FB-` + `<nonce>` + `-END` (no spaces). Inside: files and lines changed; summary; result of each verification command; commit hash; anything not done and why." The agent assembles the closing line, so the brief echoed on screen cannot match it. Poll in the background, about 20 minutes at most: every 20 s `ORCA terminal read --terminal <h> --limit 400 --json`, join `result.terminal.tail`, and stop when it contains `FB-<nonce>-END`; then verify as in loop step 5. On timeout read the screen and tell the user where the agent is; do not send more input unless the user asks. Which non-Claude/Codex agents ignore the preamble is **not yet verified**: the spike only tested Claude, and a Grok/Gemini behavior is unproven. Treat them as Branch A candidates only after the user agrees or the first attempt shows no `worker_done`. Branch A agents still complete through the gate: their brief's completion line is `bash SKILL/scripts/orca-done.sh --task <label> --checklist <path> --fb-nonce <nonce> --summary "..."`, which verifies the checklist and then prints the `FB-START ... FB-<nonce>-END` block itself (details in `references/multi-agent-anti-skip.md`). <!-- anti-skip:multi-agent:brancha -->

**Branch B, preamble-capable agent that finishes without sending `worker_done`.** Absence never authorizes abandon. `worker-abandon --dispatch <id>` only with positive proof: `ORCA orchestration worker-read --dispatch <id> --source transcript` shows the agent's final turn sent no `worker_done`, or an `FB-<nonce>-END` block has appeared. An empty wait, a timeout, an unchanged tail, or `unverifiable` liveness is only a checkpoint: keep `check --wait` or follow `worker-list` `projection.nextAction`. After abandon, retry with `worker-start --retry-of <dispatch_id>` or switch that terminal to Branch A.

## Pitfalls

- `worktreePath` differing from the pane (even the same agent type): not eligible. The parent repo counts; a submodule path does not.
- `ORCA status --json` has no caller handle outside a terminal; do not infer self from it.
- `--worktree current` outside a terminal silently resolves to the coordinator's worktree; pass `path:"<pane>"`.
- `worker-start` can exit 1 with `ok:true` and `state:failed`; it still creates a Task + Dispatch: `worker-release` it and `task-update --status failed` if dropped.
- Busy start (`already has an active dispatch`): wait or pick another terminal, never retry the same command.
- Agent stuck on a dialog (for example a usage-credits prompt) still returns `input_accepted`; only send Enter to terminals you own.
- `tui-idle` is not completion. Use `worker_done` (or the nonce in Branch A).
- Never `terminal close` an owned worker (use `worker-release`); never close a user's terminal.
- Ack a Delivery only after every message in it is handled; a bound Run replays it otherwise.
- `worker_done` settles the Task automatically; do not also `task-update --status completed`.
- Several agents share one worktree: tell each its branch and forbid `git add -A`; a Codex sandbox may not write `.git`, so verify the tree and commit on its behalf.
- Heartbeats come every ~5 minutes from workers; a quiet worker inside `ask` or `check --wait` is alive.
