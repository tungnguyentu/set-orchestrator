# Setup, status and off (detail)

The `on`, `status` and `off` procedures of `/set-orchestrator`. `ORCA` is the resolved Orca executable (SKILL.md section 0); scripts are called by path relative to the skill directory.

## `on [objective] [--from <handle>] [--open <agent>[:<count>][@<model>[/<effort>]],...] [--skills ak|ce|superpowers|none]`

1. `ORCA status --json` to confirm the app is up.
2. Self handle: `bash scripts/self-handle.sh [--from <handle>]`. Two session kinds, both supported:
   - **Orca terminal** (Claude TUI in a terminal tab): prints `$ORCA_TERMINAL_HANDLE` (`term_…`). Orchestration commands outside that terminal need `--from $SELF` / `check --terminal $SELF`.
   - **Orca chat tab** (Chat UI, a "structured" session): no terminal, not a `terminal list` row, `ORCA_TERMINAL_HANDLE` empty, but Orca injects `ORCA_AGENT_SESSION_ID`; the script prints the mailbox address `orca_session_id:<id>` (`ORCA status --json` shows the same under `caller.orcaSessionId`). Orchestration commands already act as this session: give `--from`/`--terminal` either this exact address or nothing, never another handle (Orca refuses: `consumer_fenced`), and a chat can never be named from another shell (`session_caller_chat_not_declarable`). `terminal send/rename/read/wait` cannot target a chat, so the self-directed parts of steps 9, 10 and the own-context rule (`coordinator-loop.md`, "Own context") are replaced by asking the user (below).
   - Exit 2 means both variables are empty, so this shell is outside Orca, or a terminal whose shell lost its handle; for the latter run the two-step probe in two separate Bash calls: `bash scripts/self-handle.sh --nonce` (prints `ORCH-SELF-…`, which now shows on this session's own screen), then `bash scripts/self-handle.sh --probe ORCH-SELF-… --pane "$PWD" [--orca <ORCA>]`, which reads every connected Claude terminal of the pane and prints the one whose screen shows the nonce (`--json` adds title and pane; exit 3 none, retry from `--nonce`; exit 4 several, show the user the stderr candidates and ask). A handle the user gives goes in as `--from`. Never pick a handle by tab title alone. Tell the user which handle or address you use before creating a Run.
3. Pane path = `worktreePath` of the self terminal (from `terminal list`); for a chat session, the worktree that contains `$PWD` (`ORCA worktree ps --json`, `path`).
4. `ORCA orchestration run-current [--from $SELF]`. If a Run is bound, reuse it; otherwise `ORCA orchestration run-create --objective "<objective or 'orchestrate <pane>'>" [--from $SELF]`.
5. Open agents (only with `--open`, or when the user asks in words, for example "mở thêm 2 claude và 1 grok"): `bash scripts/open-agents.sh --pane "<pane path>" --open <spec> --next <n>` with `<spec>` such as `claude:2,grok,codex,agy` or, with a model and effort per entry, `claude:2@sonnet,claude@opus/high,codex` (`<agent>[:<count>][@<model>[/<effort>]]`; without `@model` the agent uses its default) and `<n>` the next free roster number. It runs `ORCA terminal create --worktree path:<pane> --title <agent>-<n> --command <launch>` per agent, where `<launch>` sets the permission mode: Claude `cc-launch --permission-mode auto` (bypass is disabled in the global settings; inherits your `CLAUDE_CONFIG_DIR`, so the worker uses your account and the shared Serena), Grok `--permission-mode bypassPermissions`, Codex `--dangerously-bypass-approvals-and-sandbox`, Antigravity (`agy`) `--dangerously-skip-permissions`. It then waits for `tui-idle` and `agentIdentity`, printing one JSON row per terminal (`handle, agent, title, ok, error, model, effort`); copy `model` and `effort` into that terminal's `roster[]` entry. A row with `ok:false` is reported to the user as is; never retry the launch blindly. Terminals it opened are yours: `ORCA terminal close --terminal <h>` on `off` when the user agrees.
6. Roster: `ORCA terminal list --json | python3 scripts/pane-roster.py --pane "<pane path>" --self $SELF` (`--json` for machine use). Eligible rows = same pane + agentIdentity set + connected + writable + not busy + not self. Chat tabs are not terminals, so they never appear as workers; open terminal agents with `--open`. If none are eligible, say so plainly and stop: ask the user to open an agent in this pane or to rerun with `--open`.
7. Skill family. `--skills` wins; otherwise detect from this session's config dir `${CLAUDE_CONFIG_DIR:-$HOME/.claude}`: `skills/ak-cook` present means `ak`; else a `plugins/cache/*/compound-engineering` directory means `ce`; else `plugins/cache/*/superpowers` means `superpowers`; else `none`. Store it as `skill_family`; it picks the Method and Context lines that step 8b writes into the pane's worker contract (table in `coordinator-loop.md`). Workers started from another config dir or another machine may differ: when a `worker_done` body says the skill is not installed, tell the user and suggest `--skills`.
8. Write the state file (`mkdir -p` its directory).
   8b. Worker contract (once per pane, not per worker): `bash scripts/install-worker-contract.sh --pane "<pane path>" --skill "<abs skill dir>" --family <skill_family> [--orca <resolved ORCA>]`. It writes `<pane>/.orca/worker-contract.md` from `references/worker-contract.md` with this skill's absolute path and the family's Method/Context lines, and adds `.orca/` to `.git/info/exclude`. After a skill update that changed the contract's fixed text, rerun once with `--force`. Rerunning is safe: an existing file only gets its skill/Method/Context blocks refreshed (`--force` rewrites it whole). If `--skills` changes later, rerun with the new family.
9. Auto-compact window. For every eligible Claude terminal (`agent` starts with `claude`): `ORCA terminal wait --terminal <h> --for tui-idle --timeout-ms 60000`, then `ORCA terminal send --terminal <h> --text "/autocompact 300k" --enter --wait-submit 15 --json`; record the handle in the state file's `autocompact[]` list. Queue the same input to yourself: `ORCA terminal send --terminal $SELF --text "/autocompact 300k" --enter` (it runs when this turn ends); in a chat session that is impossible, so ask the user to type `/autocompact 300k` in this tab and record `self: user` in `autocompact[]`. The command persists `modelSettings.<model>.autoCompactWindow: 300000` in that session's `settings.json`, so it is cheap to repeat. Skip Codex, Grok and Gemini terminals (no such command).
10. Names. `ORCA terminal rename --terminal $SELF --title "orchestrator"` (skip for a chat session; the user may rename the tab), then every eligible worker: `ORCA terminal rename --terminal <h> --title "<agent>-<n>"` (agent type plus its position in roster order; terminals from step 5 already carry such a title, keep it). Store each title in the state file `roster[]` entry. Orca prepends its own status glyph; never include one in the title.
11. Tell the user: "This session is now orchestrator for pane X, Run R, N agents: ..." and say that from now on implementation requests go through the dispatch loop. Also check the role-restore hook: `grep -q orchestrator-resume-hook.sh "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/settings.json"`. When it is absent, say so once in this message: without it this session forgets its workers after `/compact`, and `references/orchestrator-hook.example.json` shows what to merge into that settings file. Do not edit the settings file unless the user asks.

Outside an Orca terminal, `run-create`, `run-current`, `send`, `reply`, `task-create`, `task-update`, `dispatch`, `worker-start` need `--from $SELF`; `check` needs `--terminal $SELF` and rejects `--from`; `worker-list/show/read/release/retain/abandon` need neither. In a chat session every command acts as the session on its own; `--from`/`--terminal` may only repeat `$SELF` (the `orca_session_id:` address), which is what `dispatch.sh` and `settle.sh` do.

## `status`

Read the state file for this self handle (a fresh session outside Orca does not know it: `ls "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/orchestrator/"`; one file means that handle, several means ask the user). If `<pane path>/plans/handoffs/session-handoff.md` exists and is newer than the state file's `started`, read it first: it is the continuation contract written before the last compaction. Then `run-current [--from $SELF]`, `ORCA orchestration worker-list --run <run_id> --json`, and the current roster. Print Run, pane, active/settled dispatches, and who owes a decision. Use it to restore the role after compaction or in a fresh session (if the state file is missing, say the role is not active).

## `off`

1. `ORCA orchestration worker-list --run <run_id> --terminal-state reclaimable --json`; for each row still owing a decision, ask the user or `worker-retain`; run `worker-release` only when told to or when it is the owned worker you created. Terminals the user opened come back `retained/external_terminal` and are never closed.
2. Active Dispatches: tell the user; do not abandon or stop without their word.
3. Terminals in `opened[]` that are idle: ask the user once whether to close them, then `ORCA terminal close --terminal <h> --json` for each agreed handle. No `reset`. Delete the state file. Tell the user the role is removed.
